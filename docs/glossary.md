# Словарь архитектора тестирования

Термины, которые используются в проекте. Колонка «В Slot» показывает, где термин живёт у нас или в какой итерации появится. Новый термин в документах сначала добавляется сюда.

## Решения и документы

| Термин | Что это | В Slot |
|---|---|---|
| ADR (Architecture Decision Record) | Запись одного архитектурного решения: контекст, решение, последствия, отвергнутые альтернативы. Одна страница, хранится рядом с кодом. Принятый ADR не переписывают, а заменяют новым | [docs/adr](adr) |
| RFC (Request for Comments) | Предложение до решения: проблема и варианты, по которым собирают возражения. Итог RFC обычно фиксируется как ADR | с итерации 1 |
| C4 | Способ рисовать архитектуру на четырёх уровнях детализации: Context (система и её окружение), Container (сервисы и хранилища), Component, Code | [architecture.md](architecture.md), уровень Container |
| Тестовая стратегия | Какие риски какими уровнями тестов закрываем, что не автоматизируем и почему, какие gates | [test-strategy.md](test-strategy.md) |
| Fitness function | Автоматическая проверка архитектурного свойства: скорости, зависимостей между слоями, производительности. Термин из книги Building Evolutionary Architectures | бюджет времени CI (ADR-0004) |

## Уровни тестов и модели

| Термин | Что это | В Slot |
|---|---|---|
| Unit | Код в процессе теста, всё внешнее (сеть, база, время) заменено | `tests/unit` |
| Component | Один сервис целиком и его настоящая база в контейнере; соседние сервисы — заглушки | `tests/component` |
| Contract | Проверка, что поставщик API отдаёт то, что ожидает потребитель, без совместного запуска обоих | итерация 2 |
| Smoke | Быстрая проверка «система поднялась и отвечает» на реальном стенде | `tests/smoke` |
| E2E (end-to-end) | Сценарий через интерфейс на полном стеке. Самый дорогой и хрупкий уровень, держим единицы | итерация 4 |
| Пирамида тестов | Модель: много быстрых нижних тестов, мало e2e. Варианты: trophy (упор на интеграционные тесты, фронтенд), honeycomb (Spotify, упор на тесты сервиса с зависимостями) | — |
| SMURF | Модель Google вместо «формы»: набор тестов оценивается по Speed, Maintainability, Utilization (расход ресурсов), Reliability, Fidelity (похожесть на прод) | язык для ADR |

## Изоляция и контракты

| Термин | Что это | В Slot |
|---|---|---|
| Stub, mock, fake | Замены настоящей зависимости. Stub возвращает заготовленный ответ. Mock ещё и проверяет, как его вызвали. Fake — упрощённая рабочая реализация, например база в памяти | платёжный провайдер (итерация 2) |
| Testcontainers | Библиотека: тест сам поднимает настоящую базу или очередь в Docker и убирает после себя | Postgres в `tests/component` |
| WireMock | HTTP-сервер-заглушка: отвечает по заданным правилам, умеет имитировать ошибки и задержки | соседи в component-тестах, PayStub в стеке |
| Внедрение отказов (fault injection) | Намеренные сбои соседа в тесте: `500`, зависание дольше таймаута, обрыв соединения, пустой ответ | тесты с WireMock |
| Таймаут | Предел ожидания ответа соседа. Без него зависший сосед подвешивает и наш сервис | `payments_timeout`, `http_timeout` |
| CDC (consumer-driven contracts) | Потребитель записывает, что он ожидает от API; поставщик в своём CI проверяет, что выполняет это. Инструмент — Pact | `contracts/pacts/` |
| Pact-файл | Записанный контракт: запросы потребителя и та часть ответов, которую он читает | `booking-payments.json`, `payments-booking.json` |
| Состояние поставщика (provider state) | Предусловие взаимодействия, например «бронь существует». Поставщик готовит его перед проверкой | `given(...)` в тестах, обработчик в `test_pact_provider.py` |
| can-i-deploy | Вопрос «совместима ли эта версия с тем, что уже развёрнуто». У нас — проверка поставщика против pact-файлов из `main` | `make base-pacts` |
| Ломающее изменение (breaking change) | Изменение API, после которого существующий клиент перестаёт работать: удалили поле ответа, добавили обязательное поле запроса | oasdiff |
| Снимок схемы | Схема API, сгенерированная из кода и закоммиченная; расхождение с кодом — ошибка | `services/*/openapi.json` |
| OpenAPI | Машиночитаемое описание HTTP API. FastAPI генерирует его сам; по нему проверяют контракты и генерируют клиентов | `services/*/openapi.json`, `contracts/paystub/openapi.yaml` |
| Фаззинг | Автоматическая генерация неожиданных входных данных для поиска падений. По схеме API — Schemathesis | `test_fuzz.py` |
| Property-based testing | Тест задаёт свойство («никогда не `5xx`»), а примеры генерирует библиотека (Hypothesis) и сама уменьшает найденный пример до минимального | под капотом Schemathesis |
| Закрепление по digest | Образ Docker указывается по хэшу содержимого, а не по тегу вроде `latest`, который может измениться | oasdiff в Makefile |
| Version skew | Расхождение версий: в проде одновременно работают разные версии сервисов. Причина большинства контрактных аварий | ADR-0002 |

## Пайплайн

| Термин | Что это | В Slot |
|---|---|---|
| CI / CD | Continuous Integration: каждое изменение автоматически проверяется. Continuous Delivery / Deployment: каждое проверенное изменение готово к выкатке / выкатывается автоматически | [ci.yml](../.github/workflows/ci.yml) |
| Pipeline, job, step, runner | Пайплайн состоит из задач (job), задача — из шагов (step). Задачу выполняет машина-раннер | задачи `checks` и `stack-smoke` |
| Quality gate | Автоматическая проверка с порогом, которая блокирует изменение | таблица в [test-strategy.md](test-strategy.md) |
| Храповик (ratchet) | Порог, который можно только ужесточать | покрытие ≥ 90% |
| Время обратной связи (feedback time) | Время от пуша до результата проверки | бюджеты 5 и 10 минут |
| Эфемерное окружение | Полный стек, который создаётся под одну проверку или один PR и затем уничтожается | задача `stack-smoke` (ADR-0003) |
| Healthcheck | Эндпоинт или команда, по которой оркестратор понимает, что сервис готов | `/health`, `HEALTHCHECK` в Dockerfile |
| TIA (test impact analysis) | Запуск только тех тестов, которые затронуты изменением | `tools/changed_services.py`, задача `changes` |
| Шардирование (sharding) | Деление набора тестов на части, которые идут параллельно на разных машинах | позже |
| Lock-файл | Точные версии всех зависимостей, чтобы сборка была одинаковой везде | `uv.lock` |
| Миграция | Версионированное изменение схемы базы, которое применяется по порядку и умеет откатываться | `booking/migrations` |
| Одноразовый контейнер (init job) | Контейнер, который выполняет задачу и завершается; остальные ждут его успешного выхода | `booking-migrate` |

## Безопасность

| Термин | Что это | В Slot |
|---|---|---|
| SCA (software composition analysis) | Проверка чужого кода в зависимостях на известные уязвимости. Сравнивает версии из lock-файла с базой advisory | `make audit` (ADR-0018) |
| SAST | Статический анализ своего кода на опасные конструкции: конкатенация SQL, `subprocess` с shell, слабая криптография | правила `S` в ruff |
| DAST | Проверка запущенного приложения снаружи, как это делал бы атакующий | итерация 6, ZAP |
| SBOM (software bill of materials) | Машиночитаемый список всего, из чего собран продукт. Нужен, чтобы за минуты ответить «а есть ли у нас уязвимый пакет X» | итерация 6 |
| Advisory | Публикация об уязвимости. Один и тот же баг живёт под несколькими идентификаторами: CVE (глобальный номер), GHSA (запись GitHub), PYSEC (запись Python), OSV (общая база, бесплатная) | `tools/dependency_audit.py` сводит их в одну находку |
| CVSS и уровень серьёзности | Оценка опасности уязвимости. CVSS — балл от 0 до 10 и вектор; GitHub переводит балл в слово: LOW, MODERATE, HIGH, CRITICAL | пороги в ADR-0018 |
| Поиск секретов (secret scanning) | Поиск паролей, ключей и токенов в коде и в истории коммитов. История важнее рабочего дерева: удалённый секрет остаётся в объектах git | `make secrets`, gitleaks |
| Список принятых рисков (risk acceptance) | Файл с уязвимостями, с которыми решили жить: причина, владелец, дата пересмотра. Просроченная запись роняет сборку | `security/accepted-risks.toml` |
| Срок на исправление (remediation SLA) | Сколько времени даётся на устранение находки до того, как она начнёт блокировать. У нас считается от даты публикации advisory | 30 дней для MODERATE и LOW |
| Список исключений (allowlist) | Что сканеру разрешено не замечать. Сила сканера обратно пропорциональна длине этого списка, поэтому он фиксируется тестом | `security/gitleaks.toml` |
| Fail closed / fail open | Поведение проверки при неопределённости. Fail closed — «не знаю, значит блокирую», fail open — «не знаю, значит пропускаю» | неоценённый advisory блокирует |
| Усталость от алертов (alert fatigue) | Состояние, когда сигналов так много, что их перестают читать и начинают обходить. Главный враг любого gate безопасности | аргумент в ADR-0018 |
| Цепочка поставок (supply chain) | Всё, через что чужой код попадает в наш продукт: пакеты, базовые образы, действия CI. Атака на неё дешевле атаки на сам продукт | lock-файлы, образы по digest |

## Надёжность тестов

| Термин | Что это | В Slot |
|---|---|---|
| Flaky-тест | Тест, который на одном и том же коде то проходит, то падает | Quality Hub (итерация 5) |
| Карантин | Flaky-тест исключён из блокирующих gates, но продолжает запускаться; у него есть владелец и срок | итерация 5 |
| Flakiness rate | Доля нестабильных результатов | итерация 5 |
| Mutation testing | Инструмент намеренно портит код («мутант»). Если тесты не упали, они слабые. Mutation score — доля пойманных мутантов. Лучший способ проверить качество тестов, в том числе написанных AI | `make test-mutation`, mutmut |
| Выживший мутант | Изменение кода, которое не заметил ни один тест. Либо тест слабый, либо изменённый код не влияет на поведение (например, текст сообщения) — второе решается осознанно, а не игнорируется | `mutmut results` |
| Граничное значение | Значение на границе условия: «ровно сейчас», «ровно 64 символа». Именно там живут ошибки `<` против `<=` | тест `starts-exactly-now` |

| Термин | Что это | В Slot |
|---|---|---|
| DORA | Пять метрик поставки: частота деплоев, время от коммита до прода (lead time), доля неудачных изменений (change fail rate), время восстановления после неудачного деплоя, доля незапланированных переделок (rework rate) | итерация 5 |
| Escaped defects | Дефекты, найденные после релиза. Главная метрика эффективности всей системы тестирования | — |
| SLO (service level objective) | Целевой уровень качества сервиса, например «95% запросов быстрее 300 мс» | итерация 6 |
| p95, p99 | Перцентили: 95% (99%) запросов быстрее этого значения. Среднее скрывает медленные хвосты | итерация 6 |
| ROI автоматизации | (выгода − затраты) / затраты. Частая ошибка — не учитывать поддержку тестов и разбор flaky | — |

## Архитектура продукта

| Термин | Что это | В Slot |
|---|---|---|
| Testability | Насколько систему легко проверять: можно ли управлять её состоянием и временем, видно ли, что внутри, изолируются ли части. Требование к продукту, а не к тестам | `/health`, `build_sha` |
| Идемпотентность | Повторный вызов даёт тот же результат, что и первый. Критична для платежей и повторных сообщений | ADR-0008: естественные ключи в базе |
| Естественный ключ | Бизнес-признак, по которому повтор узнаётся без специального ключа: «одна оплата на бронь», «одно событие провайдера» | `uq_payments_booking_id`, `provider_events` |
| Ключ идемпотентности (Idempotency-Key) | Заголовок, по которому сервер узнаёт повтор запроса и возвращает прежний результат. Так работает Stripe | вызов PayStub |
| Вебхук | HTTP-запрос, которым внешняя система сообщает о событии: «оплачено» | `/webhooks/paystub` |
| Доставка «хотя бы один раз» (at-least-once) | Гарантия, что сообщение дойдёт, но возможно не один раз. Получатель обязан быть идемпотентным | вебхуки PayStub |
| HMAC-подпись | Отпечаток тела сообщения, сделанный общим секретом. Доказывает, что сообщение отправил владелец секрета и его не изменили в пути | `PayStub-Signature` |
| База на сервис (database per service) | Каждый сервис владеет своей базой, чужие таблицы не читает | `booking-db`, `payments-db` |
| Race condition (гонка) | Результат зависит от порядка одновременных операций. Пример: двое бронируют один слот | `test_booking_race.py` |
| Check-then-act | «Проверил, потом сделал»: между проверкой и действием состояние успевает измениться. Самый частый вид гонки | наивная версия бронирования (ADR-0005) |
| Инвариант | Правило, которое должно выполняться всегда, при любом порядке операций. Пример: у слота не больше одной активной брони | ADR-0005 |
| Частичный уникальный индекс | Уникальность только для строк, подходящих под условие. У нас: один `slot_id` среди броней в статусах `pending` и `confirmed` | `uq_bookings_active_slot` |
| Условное обновление | `UPDATE … WHERE` с проверкой ожидаемого состояния. Если строка не изменилась, значит, её успел поменять другой запрос | смена статуса брони |
| Транзакция | Группа операций с базой, которая выполняется целиком или не выполняется вовсе | каждая операция сервиса |
| Управляемые часы (fake clock) | Код получает текущее время параметром, а тест сам решает, который час. Позволяет проверить «слот только что начался» без ожидания | `FixedClock` |
| Liveness и readiness | Liveness — процесс жив. Readiness — готов обслуживать запросы, например видит базу. Оркестратор по-разному реагирует на их отказ | `/health` — liveness; `/ready` в «Долгах» |
| Распределённый монолит | Сервисы разделены сетью, но не могут выкатываться независимо | ADR-0002 |
| Монорепозиторий | Все сервисы в одном репозитории | ADR-0002 |

## События и очереди

| Термин | Что это | В Slot |
|---|---|---|
| Событие и команда | Событие — факт, который уже случился («бронь подтверждена»); у него может не быть получателя. Команда — просьба что-то сделать, у неё есть адресат и она может быть отклонена | `booking.confirmed` — событие; `booking.confirm` в outbox `payments` — команда |
| Брокер | Посредник, который принимает сообщения и отдаёт их потребителям, переживая их недоступность | Redis Streams (ADR-0009) |
| Поток и группа потребителей | Поток — упорядоченный журнал сообщений. Группа потребителей делит его между несколькими процессами так, что каждое сообщение достаётся одному из них | `slot.bookings.v1`, группа `notifier` |
| Ack и список необработанных (PEL) | Потребитель подтверждает обработку (`XACK`). Всё, что выдано и не подтверждено, лежит в списке необработанных и может быть выдано снова | `XACK`, `XAUTOCLAIM` в `notifier/consumer.py` |
| At-least-once / at-most-once / exactly-once | Доставка «хотя бы один раз» допускает дубликаты, «не более одного раза» — потери, «ровно один раз» между двумя системами невозможна: её изображают из первой плюс идемпотентности получателя | ADR-0010 |
| Transactional outbox | Сообщение пишется в таблицу той же транзакцией, что и изменение данных. Отдельный процесс публикует его позже. Убирает окно «записал, но не опубликовал» | `outbox_messages`, ADR-0010 |
| Relay (publisher) | Процесс, который читает outbox и публикует сообщения. Единственное место, которое знает про брокер | `booking-relay`, `payments-relay` |
| Идемпотентный потребитель | Потребитель, который обрабатывает одно и то же сообщение дважды без последствий: ключ сообщения записан в его базе | `processed_events` в `notifier` |
| Очередь ошибок (DLQ) | Отдельное место для сообщений, которые не удалось обработать за N попыток. Нужна, чтобы одно сообщение не блокировало остальные | `slot.bookings.v1.dead` |
| Ядовитое сообщение | Сообщение, обработка которого падает всегда, сколько ни повторяй | Тест «ядовитое сообщение не останавливает поток» |
| Eventual consistency | Состояние систем сходится не мгновенно, а через некоторое время. Требует от теста ожидания условия, а не проверки сразу после запроса | Подтверждение брони после итерации 3 |
| Polling-ассерт | Проверка «условие выполнится за T» опросом с таймаутом вместо `sleep`. При истечении времени сообщает, чего именно не дождались | `wait_until` |
| Backpressure | Ситуация, когда производитель быстрее потребителя. Признак — растущее отставание (lag) группы | Длина потока и lag — метрики итерации 5 |
