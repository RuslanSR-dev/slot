# Стратегия тестирования, версия 4

Документ живой: каждая итерация добавляет в него уровень или правило.

## Уровни тестов

Определения заданы через границу, а не через название. Большая часть споров про «unit против integration» — это споры о разных определениях.

| Уровень | Что запущено | Что заменено | Где лежит | Статус |
|---|---|---|---|---|
| unit | Код сервиса в процессе теста | Сеть, база, время | `tests/unit` | есть |
| component | Один сервис + его настоящий Postgres и настоящий Redis в контейнерах (Testcontainers) | Соседние сервисы и внешние API — WireMock по настоящему HTTP; время — управляемые часы | `services/*/tests/component` | есть |
| contract, потребитель | Настоящий клиент против mock-сервера Pact; результат — pact-файл | Поставщик | `services/*/tests/contract` | есть |
| contract, события | Потребитель объявляет, какие поля читает и какие типы обрабатывает; сверяется с опубликованной схемой события | Производитель | `services/notifier/tests/contract` | есть |
| contract, поставщик | Сервис с настоящей базой проигрывает pact-файлы потребителей из ветки и из `main` | Соседи — WireMock | `services/*/tests/component/test_pact_provider.py` | есть |
| фаззинг | Сервис с настоящей базой получает сгенерированные по его схеме запросы | Соседи отвечают успешно | `services/*/tests/component/test_fuzz.py` | есть |
| smoke | Вся система из `compose.yaml`, чёрный ящик | Только внешний провайдер (WireMock) | `smoke/` | есть |

e2e через интерфейс — только критические сценарии, единицы штук. Всё, что можно проверить уровнем ниже, проверяется уровнем ниже.

## Какой риск каким уровнем закрыт

| Риск | Уровень | Почему именно там |
|---|---|---|
| Недопустимый переход статуса брони, слот в прошлом, некорректный слот | unit | Чистая логика без базы; все комбинации перебираются за миллисекунды |
| Unit-тесты домена проходят, но не заметили бы ошибку в логике | mutation testing | Покрытие показывает, какие строки выполнились, но не то, проверены ли они |
| Два клиента одновременно заняли один слот | component, тест на гонку | Гонку видно только на настоящей базе и при одновременных запросах (ADR-0005) |
| Ответы API: коды, ошибки, фильтры | component | Нужна настоящая база: коды `409` рождаются из её ограничений |
| Бронирование в момент начала слота | component, управляемые часы | Время двигает тест, а не реальность |
| Забыли миграцию; миграция не откатывается | component, тесты миграций | Миграции — код, который в проде запускается один раз и без права на ошибку |
| Условие индекса разошлось с `ACTIVE_STATUSES` в коде | component, отдельный тест | Alembic не сравнивает условия индексов |
| Повтор запроса или вебхука создал второй платёж или второе подтверждение | component, тесты повторов и гонок | Дубликаты разводит база (ADR-0008); одновременные дубликаты — отдельный тест с барьером |
| Сосед упал, завис, оборвал соединение | component, WireMock с отказами | Настоящие сетевые отказы; таймауты в тестах короткие, чтобы тест шёл доли секунды |
| Вебхук подделан или изменён в пути | unit (подпись) + component (ответ 401, событие не записано) | Проверка подписи — чистая функция; её сила доказана mutation testing |
| Бронь истекла, но слот остался занятым | component, управляемые часы | Граница «ровно через 15 минут» проверяется точно |
| Образ не собирается, миграции не применились, сервис не видит базу или соседа | smoke | Проверяется только на собранном стеке |
| Сквозной путь «бронь → оплата → подтверждение» не работает | smoke | Единственное место, где все сервисы работают вместе |
| Поставщик изменился так, что потребитель сломается | contract (Pact) | Проверяется только то, что потребитель реально использует; без совместного запуска |
| Новый поставщик выкатится раньше нового потребителя (version skew) | contract, pact-файлы из `main` | Ветка согласована сама с собой; ломается пара «новый + развёрнутый» |
| Ломающее изменение публичного API | схема, oasdiff против `main` | Покрывает весь API, включая неизвестных потребителей |
| Схема API разошлась с кодом | снимок схемы | Схема генерируется из кода и сравнивается с закоммиченной |
| Неожиданный ввод даёт `500` или ответ не по схеме | фаззинг | Человек не придумает NUL-байт и число больше 2³¹; генератор придумает |
| Заглушка внешнего API разошлась с настоящим API | сверка заглушек со схемой PayStub | Иначе тесты зелёные против API, которого не существует |
| Событие потеряно: сервис упал между изменением состояния и публикацией | component, тест с недоступным брокером | Записи и публикации нет в одной транзакции; outbox превращает потерю в повтор (ADR-0010) |
| Одно событие доставлено дважды | component, тест на дубликат | At-least-once — это норма; разводит первичный ключ `event_id` в базе потребителя |
| Уведомление ушло клиенту дважды | component, тесты падения до и после отправки | Физически запрос уходит дважды; один ключ идемпотентности делает из него одно сообщение |
| События пришли не в том порядке | component, тест с обратным порядком | Группа потребителей порядок не гарантирует; событие самодостаточно, поэтому порядок не нужен |
| «Ядовитое» сообщение останавливает очередь | component, тесты нечитаемого сообщения и вечного отказа шлюза | После N доставок сообщение уходит в очередь ошибок и подтверждается |
| Сообщение взято потребителем, который умер | component, тест перезапуска другим потребителем | Без `XAUTOCLAIM` оно осталось бы в списке необработанных навсегда |
| Ломающее изменение схемы события | снимок схемы + `event_schema_diff` против `main` | Потребитель не отвечает «400, ты меня сломал»; узнать об этом иначе негде |
| Потребитель читает поле, которого производитель больше не шлёт | contract, события | Проверяется до запуска обоих сервисов |
| Результат появляется не мгновенно (eventual consistency) | smoke, ожидание конечного состояния опросом | Проверка сразу после запроса поймала бы промежуточное состояние |
| Запущена не та сборка | smoke | ADR-0003 |
| В зависимости известная уязвимость | SCA по lock-файлам (`make audit`) | Проверяется ровно то, что установится; наш код тут ни при чём, поэтому уровень теста не помогает |
| Уязвимость пропустили и забыли | список принятых рисков со сроком | Отличить решение от забытой дыры можно только по дате пересмотра (ADR-0018) |
| Секрет попал в репозиторий или в историю коммитов | поиск секретов (`make secrets`) | Удаление следующим коммитом не помогает: значение остаётся в объектах git и уже скопировано |

## Quality gates в пайплайне

| Gate | Задача CI | Порог | Зачем |
|---|---|---|---|
| Форматирование и линтер (ruff, включая правила безопасности `S`) | checks | 0 нарушений | Ревью человека — про смысл, а не про стиль |
| Строгая типизация (mypy strict) | checks | 0 ошибок | Детерминированная проверка AI-кода до запуска |
| Unit-тесты | checks | все зелёные | Быстрая обратная связь без Docker |
| Mutation score доменных правил (mutmut) | checks | 100%, только растёт | Проверка качества самих тестов, в том числе написанных AI |
| Тесты потребителей, pact-файлы закоммичены | checks | все зелёные, `git status` чист | Контракт меняется только осознанно, через ревью |
| Схема API совпадает с кодом | checks | без расхождений | ADR-0007 |
| Нет ломающих изменений API против `main` | checks | 0 ошибок oasdiff | ADR-0007 |
| Схема события совпадает с кодом | checks | без расхождений | ADR-0010 |
| Нет ломающих изменений схемы события против `main` | checks | 0 нарушений `event_schema_diff` | ADR-0010 |
| Ожидания потребителя события выполняются производителем | checks | все зелёные | ADR-0010 |
| Тесты инструментов репозитория | checks | все зелёные | Анализ влияния решает, какие gates запустятся, поэтому тестируется как gate |
| Сервисы не импортируют код друг друга (fitness function `import_boundaries`) | checks | 0 нарушений | ADR-0002: общий импорт убивает контракт между сервисами и заставляет выкатывать их вместе |
| Component-тесты | component | все зелёные | Поведение на настоящей базе и настоящем брокере |
| Проверка поставщика по pact | component | все взаимодействия из ветки и из `main` | ADR-0007 |
| Фаззинг по схеме | component | нет `5xx`, коды, тела и заголовки по схеме | ADR-0007 |
| Покрытие (unit + component) | component | не ниже 90%, только растёт | Храповик, а не цель (ADR-0006) |
| Известные уязвимости в зависимостях (`uv audit` + политика) | security | CRITICAL, HIGH и неоценённые — 0; MODERATE и LOW — не старше 30 дней с публикации advisory | ADR-0018: блокирует опасное, а не всё подряд, иначе гейт начнут обходить |
| Список принятых рисков валиден и не просрочен | security | 0 просроченных, 0 записей без находки | ADR-0018: непросроченный игнор — решение, просроченный — забытая дыра |
| Секреты в рабочем дереве и во всей истории коммитов (gitleaks) | security | 0 находок | ADR-0018: секрет в истории остаётся опубликованным даже после удаления |
| Список исключений сканера секретов не растёт молча | checks | совпадает с зафиксированным в `tools/test_secret_allowlist.py` | Сканер настолько силён, насколько короток его список исключений |
| Предупреждения в тестах | все | считаются ошибками | Устаревшие вызовы ловим в день появления |
| Smoke на эфемерном стеке | stack-smoke | все зелёные, версия сборки совпадает у каждого сервиса | Образы собираются, стартуют, это именно они, и сквозной путь работает |
| Время задач CI | все | changes 2, checks 5, security 5, component 8 на каждый сервис, stack-smoke 10 минут | ADR-0004, ADR-0006, ADR-0018 |
| Выборочный запуск | changes | component только для затронутых сервисов; в `main` — всё | Экономия времени без риска: неизвестный путь запускает всё |

## Правила

1. Никаких `sleep` в тестах: ждём условие с таймаутом (`wait_until` в `tests/component/conftest.py`).
2. Повторный запуск упавшего теста — это сигнал для учёта flaky, а не способ получить зелёную сборку.
3. Тест не «лечится» автоматически. Любое изменение ожиданий теста проходит ревью человеком.
4. Порог можно ослабить только через ADR.
5. Smoke-тесты знают только URL. Тот же файл потом проверяет развёрнутый стенд, поэтому smoke создаёт уникальные данные и не рассчитывает на пустую базу.
6. Код не читает часы сам: время передаётся параметром `now`. Тест управляет временем через `FixedClock`.
7. Component-тесты используют тот же образ Postgres, что и стек. Тест на подмене базы (SQLite, моки) не доказывает поведение ограничений и конкуренции.
8. Каждый тест component-уровня начинает с пустых таблиц. Порядок тестов не важен.
9. Тест на гонку повторяет гонку несколько раундов в одном прогоне: один раунд может её не поймать.
10. Контракт ошибки — поле `error` (код), а не текст `detail`. Тесты проверяют коды; строки сообщений помечены `pragma: no mutate`, чтобы mutation testing не требовал тестов на формулировки.
11. Mutation testing охватывает `domain.py` каждого сервиса: чистую логику с быстрыми тестами. Остальные модули перечислены в исключениях явно; новый модуль нужно либо включить в мутации, либо осознанно добавить в исключения. Правило сработало в итерации 2: новый клиент платежей попал под мутации без unit-тестов, и gate упал.
12. Соседей заменяет WireMock по настоящему HTTP, а не подмена функции в коде. Так проверяются таймауты, обрывы соединения и то, что сервис действительно отправил (тело, заголовки, ключ идемпотентности).
13. Вебхук получает ошибку только тогда, когда повтор может помочь (сосед недоступен). Всё, что повтором не исправить (неизвестное событие, неизвестный платёж), подтверждается `200`, иначе провайдер будет повторять бесконечно.
14. Smoke — отдельный проект на уровне системы: знает только адреса и секрет вебхука, не импортирует код сервисов.
15. Pact — между нашими сервисами, схема — на внешних границах (ADR-0007). В контракт потребитель записывает только то, что реально читает.
16. Фаззинг в PR детерминирован (`derandomize`): gate не должен быть лотереей. Проверка `positive_data_acceptance` исключена, потому что бизнес-правила нельзя выразить в схеме; остальные проверки включены.
17. Каждая находка фаззера закрепляется обычным тестом на границу: фаззинг вероятностный, регрессионный тест — нет.
18. Предупреждения чужих библиотек глушатся только точечно: конкретное сообщение, конкретный тест, комментарий с причиной.
19. Единый формат ошибки во всём API, включая ошибки фреймворка: `{"error": код, "detail": текст}`. Все коды ответов описаны в схеме.

20. Тестовые помощники (`wiremock.py`, `wait_until`) дублируются в каждом сервисе намеренно (ADR-0011). Условия пересмотра записаны там же.
21. Асинхронный результат проверяется ожиданием **конечного** состояния, а не появления записи. Ожидание «уведомление появилось» проходит на промежуточном статусе `sending`; ждать нужно `sent`. Эта ошибка была допущена и поймана в итерации 3.
22. Падение процесса в тестах изображается исключением, которое код не ловит (`KeyboardInterrupt`). Обычное исключение проверяет обработку ошибки, а не смерть процесса: после `SIGKILL` не выполняется ни одна строка обработчика.
23. «Ровно один раз» не проверяется, потому что его не существует. Проверяется эффект: при падении в любом месте клиент получает одно уведомление, потому что повтор уходит с тем же ключом идемпотентности.
24. Потребитель обязан пережить незнакомый тип события (подтвердить и пропустить) и незнакомое поле (проигнорировать). На оба случая есть тест: иначе добавление события производителем станет аварией у потребителя.

25. Уязвимость в зависимости пропускают только записью в `security/accepted-risks.toml`: причина, владелец, дата пересмотра. Флаг `--ignore` в пайплайне запрещён — у него нет ни автора, ни срока. Просроченная запись роняет сборку, запись без находки — тоже (ADR-0018).
26. Исключение сканера секретов задаётся значением, а не файлом. Исключение по файлу глушит и тот настоящий ключ, который вставят туда позже. Каждое исключение объясняет, почему значение безопасно, и зафиксировано тестом.
27. Срок на исправление умеренной уязвимости считается от даты публикации advisory, а не от даты сборки: иначе PR краснеет из-за чужой новости, и автор учится обходить гейт.

## Что сознательно отложено

- Mutation testing не портит данные уровня модуля: таблицу переходов `ALLOWED_TRANSITIONS` и `ACTIVE_STATUSES`. Их защищают табличные unit-тесты, перебирающие все пары статусов, но mutation score этого не доказывает.
- Mutation testing для `service.py`: мутанту нужны component-тесты с базой, это десятки секунд на мутант. Вернуться, когда появится выборочный запуск.
- Нагрузочная проверка очереди: сколько событий в секунду выдерживает связка relay — брокер — потребитель и что происходит при отставании (backpressure). Итерация 6.
- Длина очереди ошибок и возраст самой старой неопубликованной записи outbox как метрики — итерация 5. Сейчас о застрявшем сообщении узнают только из теста или из базы.
- Производительность и трассировка — итерация 6.
- Из безопасности сделаны зависимости (SCA) и поиск секретов (ADR-0018). Отложены до конца итерации 6: сканирование образов, динамическое сканирование стенда (ZAP), SBOM, автоматическое обновление зависимостей. Причина в ADR-0018: каждая проверка — свой поток находок, а несколько новых потоков сразу дают шум, из-за которого гейты начинают обходить.
- Проверка готовности сервиса к работе с базой (`/ready` в отличие от `/health`) — записано в «Долги и находки».
