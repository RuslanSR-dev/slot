# ADR-0007. Контракты: Pact между нашими сервисами, схема OpenAPI на внешних границах

Статус: принято · 2026-09-19

## Контекст

`booking` и `payments` вызывают друг друга в обе стороны и выкатываются независимо, поэтому в проде неизбежно работают разные версии (version skew). Нужно ловить несовместимость до мержа, не поднимая оба сервиса вместе. Кроме того, у `payments` есть внешний провайдер PayStub: его код и CI нам недоступны, есть только опубликованная схема API.

## Решение

1. **Между нашими сервисами — контракты от потребителя (Pact).**
   - Потребитель в своих тестах описывает запросы, которые шлёт, и поля ответа, которые реально использует. Pact-файлы лежат в репозитории (`contracts/pacts/`).
   - Поставщик в своём CI проверяет, что выполняет все pact-файлы своих потребителей.
   - Поставщик проверяется против pact-файлов из ветки **и** из `main`. Так ловится несовместимость с уже развёрнутой версией потребителя, а не только с той, что лежит в том же PR. В монорепозитории это замена брокеру Pact и его проверке `can-i-deploy`.
2. **На внешних границах — схема OpenAPI.**
   - Каждый наш сервис хранит свою схему в репозитории (`services/<имя>/openapi.json`). Gate: схема сгенерирована из кода и совпадает с сохранённой.
   - Gate: ломающие изменения схемы относительно `main` (oasdiff) блокируют PR.
   - Фаззинг по схеме (Schemathesis) на уровне component: неожиданные входные данные не дают `500`, ответы соответствуют схеме.
   - Схема PayStub хранится в `contracts/paystub/`. Наши заглушки PayStub (WireMock) проверяются на соответствие ей, чтобы подделка не разошлась с настоящим API.

## Последствия

- Плюс: Pact проверяет ровно то, что использует потребитель. Поставщик свободно меняет остальное.
- Плюс: схема защищает весь API и работает там, где договориться с поставщиком нельзя.
- Цена: два инструмента и два вида тестов. Правило выбора: контракт с нашим сервисом — Pact; чужой API или публичный API — схема.
- Цена: pact-файлы в репозитории нужно держать актуальными. Gate: тесты потребителя перегенерируют файл, и расхождение с закоммиченным — ошибка.

## Реализация (итерация 2b)

- Тесты потребителей — `services/*/tests/contract`, pact-файлы — `contracts/pacts/`. Gate `make test-contract` падает, если тесты изменили pact-файл, а он не закоммичен.
- Проверка поставщиков — `services/*/tests/component/test_pact_provider.py`, против файлов из ветки и из `BASE_REF` (`make base-pacts`).
- Схемы — `services/*/openapi.json`, gates `make openapi-check` и `make openapi-breaking` (oasdiff, образ закреплён по digest).
- Фаззинг — `services/*/tests/component/test_fuzz.py`, с фиксированным зерном в PR.
- Заглушки PayStub сверяются с его схемой — `services/payments/tests/component/test_paystub_contract.py`.

## Проверено от обратного (2026-09-20)

- Поле ответа `checkout_url` переименовано в `payment_url` в одном PR вместе с клиентом `booking` и его контрактом: проверка против pact из ветки зелёная, против pact из `main` — красная («нет ключа `checkout_url`»); oasdiff — 3 ломающих изменения.
- Переименование поля ответа и новое обязательное поле запроса — oasdiff красный; новое необязательное поле ответа — зелёный.
- Заглушка PayStub без обязательного `checkout_url` — проверка по схеме красная.
- Фаззинг нашёл 5 настоящих дефектов: чужой формат ошибки и незадокументированный `400` на неразбираемом теле; неполный заголовок `Allow` в `405`; незадокументированный `200` на повторном создании платежа; `500` на сумме больше 32-битного целого; `500` на NUL-байте в идентификаторе.

## Альтернативы

- Только Pact: не подходит для внешнего провайдера, который не будет гонять наши контракты.
- Только схема: не видит, что потребитель полагается на поведение, которого в схеме нет.
- Совместный запуск сервисов (e2e) как проверка совместимости: медленно, и проверяет только версии из одного PR, а не пары «новая + развёрнутая».
