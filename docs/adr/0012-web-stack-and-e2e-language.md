# ADR-0012. Стек web-клиента и язык e2e-тестов

Статус: принято · 2026-09-20

## Контекст

Итерация 4 добавляет интерфейс: список слотов мастера, бронирование, оплата через заглушку, отмена, простейший вход клиента и мастера. Интерфейс нужен не сам по себе — без него нечего проверять уровнем e2e и нечему быть объектом для проверок доступности и визуальной регрессии.

Два вопроса связаны и решаются одной парой, а не по отдельности: язык клиента задаёт язык, на котором дешевле писать e2e.

Что уже есть и на что решение обязано опереться:

- Монорепозиторий на Python 3.14: три сервиса и проект `smoke`, у каждого свой `pyproject.toml` и lock-файл. Gates — ruff, mypy strict, предупреждения как ошибки.
- `smoke/tests/test_stack.py` уже умеет готовить данные через API: создаёт слот, бронь, подписывает вебхук, ждёт конечного состояния через `wait_until`. Правило 5 стратегии прямо говорит, что этот же файл потом будет проверять развёрнутый стенд.
- Подтверждение брони приходит не мгновенно: вебхук → outbox → relay → брокер → потребитель (ADR-0010). Интерфейс обязан это показывать, а тест — ждать условие, а не `sleep` (правило 1).
- Один человек с бюджетом до 5 часов в неделю. Каждый новый язык в репозитории — это ещё один lock-файл, ещё один набор gates и ещё один источник обновлений.

Критерии выбора:

1. **Цена поддержки для одного человека.** Сколько инструментов добавляется к тем, что уже работают.
2. **Переиспользование подготовки данных.** E2E не имеет права создавать слот и бронь кликами: это медленно и делает тест хрупким по причинам, не имеющим отношения к проверяемому сценарию.
3. **Покрытие требований итерации.** Нужны трасса, видео и логи при падении, gate доступности (axe) и визуальная регрессия с порогом.
4. **Ценность для портфолио на международном рынке.** Это учебный проект, и он же — аргумент на собеседовании.

## Варианты: клиент

| Вариант | Плюсы | Цена |
|---|---|---|
| **Серверные шаблоны (Jinja2) + HTMX**, ещё один FastAPI-сервис `web` | Тот же язык, тот же `pyproject.toml`, те же gates: ruff и mypy накрывают клиент с первого дня. Сборки нет — образ собирается так же, как остальные. Сессия — обычная cookie, без хранения токена в браузере. Обновление статуса брони после оплаты делается атрибутом `hx-trigger="every 2s"` и ложится прямо на eventual consistency из ADR-0010. HTMX — один файл ~14 КБ, без зависимостей | Нет опыта работы со сборкой фронтенда, с состоянием на клиенте и с компонентными тестами интерфейса. Сложный интерфейс на HTMX (несколько независимых областей, оптимистичные обновления) выходит дороже, чем на компонентном фреймворке |
| **React + TypeScript (Vite)**, отдельный контейнер со статикой за nginx | Опыт, который спрашивают в вакансиях: сборка, типы на границе API, генерация клиента из OpenAPI, компонентные тесты, mock сети в браузере. Открывает уровень «тесты компонентов интерфейса» между unit и e2e | Четвёртый язык и первая экосистема Node в репозитории: `package-lock.json`, eslint, tsc, vitest, обновления зависимостей, свой шаг сборки в образе и свой набор gates. Анализ влияния (`tools/changed_services.py`) надо учить новому виду проекта. Появляется свой контракт «фронт ↔ booking», который нечем проверять, кроме того же OpenAPI |
| **Статичный HTML + `fetch` без сборки** | Дешевле всех: ноль инструментов, файлы отдаёт тот же nginx | Ручное управление состоянием быстро превращается в нечитаемый код. Для портфолио не значит ничего: это не выбор, а его отсутствие |

## Варианты: язык e2e

| Вариант | Плюсы | Цена |
|---|---|---|
| **Playwright на Python** (`pytest-playwright`) | Живёт в существующем проекте рядом со `smoke`: подготовка данных — это уже написанный код на `httpx2`, те же фикстуры, тот же `wait_until`, то же правило «ждём конечное состояние». Ноль новых языков и lock-файлов. Трасса, видео и скриншоты при падении — флагами `--tracing=retain-on-failure --video=retain-on-failure`. mypy strict и ruff накрывают e2e без настройки | Библиотека одна и та же, а **раннер** — нет. В `pytest-playwright` нет встроенного сравнения снимков (`toHaveScreenshot`), поэтому визуальную регрессию придётся писать самим: снимок, порог отличий, хранение эталонов (~50 строк плюс Pillow). Нет UI-режима отладки. Плагин axe для Python (`axe-playwright-python`) живее всего сообщества не назовёшь: проверить перед выбором |
| **Playwright на TypeScript** (`@playwright/test`) | Эталонный раннер: сравнение снимков с порогом из коробки, UI-режим, просмотр трассы, `storageState` для входа, проекты и параллелизм. `@axe-core/playwright` — основной способ проверять доступность. Именно эта пара чаще всего названа в международных вакансиях на автоматизацию | Node в CI и второй набор зависимостей. Главное — подготовка данных: e2e не сможет позвать ни строки из `smoke`, её придётся написать заново на `fetch`, и она разойдётся с Python-версией. Автоповторы (`retries`) в конфигурации есть, но правилами 2 и 4 стратегии запрещены, так что часть ценности раннера нам недоступна |

## Решение

**Рекомендую пару: `web` на Jinja2 + HTMX, e2e на Playwright под Python, в новом проекте `e2e/` рядом со `smoke/`.**

Обоснование по критериям.

*Подготовка данных решает.* Требование «данные готовятся через API» в связке с TypeScript означает второй клиент к нашему API — на другом языке, с другой моделью ошибок, без mypy и без общих помощников. Это не гипотетический риск: `smoke` уже содержит подпись вебхука HMAC и ожидание конечного состояния. На Python сценарий e2e начинается с трёх вызовов того же кода, на TypeScript — с переписывания этого кода.

*Цена поддержки.* React добавляет экосистему, которую нужно обновлять, и делает это ради интерфейса из четырёх экранов. При 5 часах в неделю это время уходит из итерации 5 (Quality Hub), которая для роли архитектора важнее интерфейса.

*Требования итерации выполнимы обоими.* Трасса, видео и логи — бесплатно в обоих. Разница ровно одна и она измерима: визуальная регрессия на Python пишется руками (снимок в контейнере, сравнение с порогом, эталоны в репозитории). Это ~50 строк и один день. Написать их самому даже полезнее: порог отличий перестаёт быть магическим числом из чужой конфигурации.

*Портфолио — единственный критерий против, и он настоящий.* «Playwright + TypeScript» встречается в международных вакансиях чаще, чем «Playwright + Python». Честный ответ: платить за это сейчас всем фронтендом не нужно. TypeScript естественно появляется в итерации 8 вместе с клиентским приложением — там он оправдан задачей, а не резюме. До тех пор аргументом служит не язык, а сам выбор: в итерации 9 этот ADR превращается в кейс «почему архитектор не потащил в проект четвёртый язык».

Что фиксируется вместе с решением:

- `web` — обычный сервис стека: свой Dockerfile, `/health` с `build_sha`, те же ограничения контейнера (`read_only`, `cap_drop: ALL`).
- `web` ходит только в `booking` по HTTP и ничего не знает о базах (ADR-0002).
- Сессия — подписанная cookie; токен в браузерном хранилище не заводим.
- E2E — отдельный проект `e2e/` со своим lock-файлом; `smoke` остаётся независимым, потому что он проверяет стенд и после деплоя, когда браузер не нужен.
- Число и состав сценариев задаёт ADR-0014, а не «сколько успеем».

## Последствия

- Плюс: в стеке появляется 13-й контейнер, но ни одного нового языка и ни одного нового вида gate. Образ `web` строится тем же способом, что и три существующих.
- Плюс: асинхронность из ADR-0010 становится видимой. HTMX опрашивает статус брони сам, и e2e проверяет то же, что увидит человек, — а не «запись в базе появилась».
- Плюс: e2e и smoke используют одинаковые помощники ожидания, поэтому правило «ждать конечное состояние, а не появление записи» действует и здесь. Эта ошибка уже была допущена в итерации 3 (правило 21) — повторять её на новом уровне не хочется.
- Цена: визуальная регрессия пишется руками; пока её нет, gate считается невыполненным, а не «сделаем потом».
- Цена: опыта разработки SPA проект не даёт. Это осознанный пропуск, а не забытый пункт.
- Цена: `tools/changed_services.py` знает сервисы списком (долг в roadmap). Добавление `web` без правки этого файла приведёт к запуску всех component-задач — безопасно, но медленно.
- Риск: HTMX хорош, пока страниц мало. Признак, что выбор пора пересматривать, — первая страница, где два независимых блока должны обновляться по разным правилам и мешают друг другу.
- Когда пересматривать: появился экран со сложным клиентским состоянием; или понадобился уровень «компонентные тесты интерфейса»; или мобильный клиент (итерация 8) всё равно приносит TypeScript, и держать два стиля дороже, чем свести к одному.

## Альтернативы

- **Vue или Svelte вместо React.** Дешевле в обучении, но цена та же — экосистема Node. Раз платить, то за то, что чаще спрашивают; раз не платить, то не платить вовсе.
- **Next.js / Nuxt (SSR-фреймворк).** Отвечает на те же вопросы, что Jinja + HTMX, но добавляет свой рантайм в стек и свою модель деплоя. Для сервера из ADR-0013 это лишние сотни мегабайт.
- **Selenium вместо Playwright.** Отдельные драйверы браузеров, нет трассы и встроенного ожидания. Единственный аргумент — распространённость в старых проектах; он не перевешивает.
- **Cypress.** Удобная отладка, но работает внутри браузера, что делает подготовку данных и работу с несколькими вкладками/сессиями неудобной. Для сценария «два клиента борются за один слот» это прямая помеха.
- **E2E на TypeScript при клиенте на HTMX.** Худшее из двух: сборка Node ради тестов, а подготовку данных всё равно придётся дублировать.
