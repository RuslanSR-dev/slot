# ADR-0009. Очередь событий — Redis Streams

Статус: принято · 2026-09-20

## Контекст

В итерации 3 `booking` сообщает о событиях брони (`booking.confirmed`, `booking.cancelled`, `booking.expired`), а `notifier` шлёт по ним уведомления. Синхронный HTTP-вызов здесь не годится: отправка уведомления не должна задерживать ответ клиенту и не должна ломать бронирование, если шлёт уведомления недоступен.

Критерии выбора:

1. **Память.** Бюджет инфраструктуры — ноль (ADR-0003). Позже стек поедет на бесплатный сервер с 512 МБ–1 ГБ памяти, где уже живут три Postgres.
2. **Гарантии.** Нужны подтверждение обработки (ack), повторная доставка после падения потребителя и место, куда убрать «ядовитое» сообщение.
3. **Цена в тестах.** Брокер поднимается в Testcontainers в каждом component-прогоне и в стеке CI. Секунды старта умножаются на число прогонов и съедают бюджет из ADR-0004.
4. **Один человек в эксплуатации.** Чем меньше движущихся частей, тем лучше.

## Варианты

| Вариант | Что даёт | Цена |
|---|---|---|
| **Redis Streams** | Группы потребителей, `XACK`, список необработанных сообщений (PEL), счётчик доставок, `XAUTOCLAIM` для зависших. Образ 28 МБ, старт меньше секунды, клиент синхронный — как весь остальной код | Нет встроенных повторов по таймеру и очереди ошибок: их пишем сами (~60 строк). По умолчанию данные только в памяти — нужна явная настройка сохранения |
| **NATS JetStream** | Те же гарантии из коробки: `ack_wait`, `max_deliver`, уведомление о превышении лимита доставок. Образ ~20 МБ | Python-клиент асинхронный. В проекте, где всё синхронно (SQLAlchemy, FastAPI-эндпоинты, тесты), появится второй стиль исполнения и свои источники нестабильности в тестах |
| **RabbitMQ** | Промышленный стандарт: dead-letter exchange, TTL, отложенные повторы — всё настройками, без кода | Erlang-рантайм: образ ~250 МБ, 100–150 МБ памяти в покое, старт в тестах — единицы секунд. Для одного потока уведомлений на маленьком сервере это плата за возможности, которые не нужны |

## Решение

Берём **Redis Streams**: одна группа потребителей на поток `slot.bookings.v1`.

Главный аргумент — не память, хотя она и решает вопрос с сервером. Главное в том, что RabbitMQ и NATS дают гарантии «настройкой», и их легко считать данностью, не понимая. В Redis Streams повторную доставку зависших сообщений и очередь ошибок пишем и тестируем сами. Для итерации, цель которой — понять гарантии доставки, это не цена, а содержание работы.

Настройки, без которых выбор не работает:

- `appendonly yes` — иначе подтверждённое, но не обработанное сообщение исчезнет вместе с перезапуском Redis;
- `XADD … MAXLEN ~ 10000` — поток не растёт бесконечно;
- имя потока содержит версию схемы события (`slot.bookings.v1`): несовместимое изменение — это новый поток, а не «сломаем на ходу».

## Последствия

- Плюс: стек в CI дорожает на 28 МБ образа и доли секунды старта.
- Плюс: клиент синхронный, потребитель — обычный цикл, его можно позвать из теста пошагово (`run_once`) и не бороться с event loop.
- Цена: логика повторов наша, значит, её нужно доказать тестами — зависшее сообщение, счётчик доставок, очередь ошибок. Это уже записано в план итерации.
- Цена: гарантия сохранности опирается на настройку Redis. Если `appendonly` выключить, тест «брокер потерял сообщение» мы не увидим — поэтому настройка живёт в `compose.yaml` рядом с комментарием, а не в чьей-то голове.
- Риск: Redis Streams не гарантирует порядок при нескольких потребителях в группе. Мы и не полагаемся на порядок (ADR-0010, п. 6).
- Когда пересматривать: появится второй-третий поток событий с разными правилами повторов, или понадобится маршрутизация по типам — тогда RabbitMQ окупится.
