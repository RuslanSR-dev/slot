# ADR-0014. Сколько e2e-тестов и какие именно

Статус: принято · 2026-09-20

## Контекст

К итерации 4 система закрыта снизу плотно: unit для правил домена, component на настоящих Postgres и Redis, контракты Pact между сервисами, снимки схем и oasdiff на границах, фаззинг, smoke на всём стеке. Цифры итерации 3: 93 + 76 + 42 теста в сервисах и 7 smoke.

Появление интерфейса создаёт соблазн переписать всё это кликами. Делать так нельзя по трём причинам, и каждая уже проявлялась в проекте:

1. **Цена времени.** Бюджет задачи `stack-smoke` — 10 минут (ADR-0004), сейчас она занимает 64 секунды. Один сценарий в браузере — это вход, переходы между страницами и ожидание асинхронного результата: десятки секунд там, где component-тест тратит доли секунды.
2. **Цена диагностики.** Красный e2e говорит «что-то сломалось в системе из 13 контейнеров». Красный component-тест говорит «сломан `payments`». Изолированность обратной связи — тот же аргумент, которым в ADR-0011 отклонён общий пакет для тестов.
3. **Цена нестабильности.** E2E — главный поставщик flaky. Итерация 5 целиком про то, как с этим жить; заводить себе работу заранее незачем.

Поэтому вопрос ставится в обратную сторону: не «что проверим через интерфейс», а **«что перестанет проверяться вообще, если интерфейса в тестах не будет»**. Сценарий попадает в список, только если ответ содержит то, чего физически нет ниже уровня браузера.

Что есть только в браузере: HTTP-клиент со своими редиректами и cookie; часовой пояс и локаль; перерисовка страницы после действия; опрос сервера, который кто-то должен включить и выключить; превращение кода ошибки в текст для человека.

## Варианты

| Вариант | Плюсы | Цена |
|---|---|---|
| **0–1 сценарий («дымовой» проход по интерфейсу)** | Почти ничего не стоит и не мигает | Не проверяются ни возврат с платёжной страницы, ни часовые пояса, ни поведение при чужой ошибке. Интерфейс остаётся непроверенным, а в итерации 4 он — главный новый объект |
| **4 сценария по правилу «только то, чего нет ниже»** | Каждый закрывает риск, которого нет ни на одном другом уровне. Держится в бюджете, и список можно защитить построчно | Требует дисциплины: любой новый e2e проходит через правку этого ADR, а не добавляется «заодно» |
| **10–15 сценариев (все пользовательские пути)** | Похоже на то, что во многих командах называют регрессией; не надо каждый раз думать | Дублирует проверенное ниже. Десяток браузерных сценариев добавит минуты и выведет задачу за бюджет. Каждый дубль ещё и мигает независимо, и удалять его будет некому: «зачем он» нигде не записано |

## Решение

**Четыре сценария. Пятый добавляется только вместе с правкой этого ADR.**

### E2E-1. Бронь, оплата и подтверждение, которое приходит само

Вход клиентом → страница мастера со свободными слотами → «Забронировать» → «Оплатить» → страница провайдера (заглушка PayStub) → возврат на наш сайт → статус брони меняется на «подтверждена» без ручной перезагрузки.

**Почему не уровнем ниже.** Smoke уже проходит цепочку `booking → payments → PayStub → вебхук → booking → outbox → Redis → notifier` и доходит до `confirmed` и `sent`. Но он сам вызывает `POST /bookings/{id}/payment` и сам подписывает вебхук. В браузере проверяются три вещи, которых нет ни в одном тесте ниже: что `checkout_url` действительно открывается, что возврат с чужой страницы приводит обратно на нашу и на нужную бронь, и что страница сама показывает переход `pending → confirmed` — то есть опрос статуса включён и потом остановлен. Забытая остановка опроса не ломает ни один тест ниже, но создаёт постоянную нагрузку от вкладки, висящей открытой сутки.

### E2E-2. Отмена своей брони и возврат слота в список

Бронь подготовлена через API → страница «мои брони» → «Отменить» → подтверждение → список слотов мастера снова показывает этот слот свободным.

**Почему не уровнем ниже.** `DELETE /bookings/{id}` и освобождение слота закрыты component-тестами ещё в итерации 1. Здесь проверяется связка двух экранов: действие на одном изменило то, что показывает второй. Закэшированный список и неперерисованный фрагмент — ошибки клиента, их не видит ни API, ни smoke. Заодно это единственное разрушающее действие в интерфейсе: сценарий нажимает кнопку дважды подряд и требует, чтобы вторая отмена не превратилась в ошибку на экране.

### E2E-3. Слот заняли, пока клиент на него смотрел

Страница со свободным слотом открыта → через API этот слот бронирует другой клиент → первый нажимает «Забронировать» → видит понятное сообщение, страница остаётся рабочей.

**Почему не уровнем ниже.** Код `409` и причина его появления доказаны на component, включая тест на гонку с несколькими раундами (ADR-0005). Но контракт ошибки у нас — `{"error": код, "detail": текст}` (правило 19 стратегии), и превращение кода в текст для человека происходит только в клиенте. «Белый экран вместо сообщения» — не дефект API, и ни один тест ниже его не увидит. Второй смысл сценария: устаревшие данные на экране объявляются штатной ситуацией, а не аварией.

### E2E-4. Мастер публикует слот — клиент видит то же время

Вход мастером → форма нового слота с датой и временем → сохранить → выход → вход клиентом → в списке мастера ровно то же время.

**Почему не уровнем ниже.** API принимает и отдаёт `starts_at` и `ends_at` в ISO с зоной, и component-тесты это проверяют. Но преобразование «то, что человек набрал в форме» ↔ UTC живёт в браузере и зависит от его часового пояса. Ни один тест на Python этого преобразования не выполняет: у процесса нет браузерной зоны. Тест обязан запускаться с явным `timezoneId`, отличным от UTC (например, `Europe/Moscow`), иначе сдвиг просто не возникнет и тест будет зелёным по совпадению. Это же единственный сценарий с двумя ролями и двумя сессиями, поэтому он заодно доказывает, что вход и выход работают.

### Правила для этих четырёх

1. Через интерфейс проходит **только то, что сценарий проверяет**. Всё остальное готовится вызовами API тем же кодом, что в `smoke` (ADR-0012).
2. Вход выполняется через API и подставляется как готовое состояние сессии (`storage_state`), кроме E2E-4, где вход и есть предмет проверки.
3. Каждый сценарий создаёт своего мастера и своего клиента с уникальным идентификатором — как `smoke` по правилу 5 стратегии. Тогда те же тесты можно гонять и против постоянного стенда, не рассчитывая на пустую базу.
4. Никаких `sleep` и никаких ожиданий «элемент появился»: ждём **конечное** состояние на экране. Ошибка с промежуточным статусом уже была допущена в итерации 3 (правило 21) и в интерфейсе повторится один в один — «оплачено» вместо «подтверждена».
5. Автоповторы упавшего e2e запрещены (правила 2 и 4 стратегии). Нестабильный сценарий — это вход в итерацию 5, а не строка в конфигурации.
6. При падении сохраняются трасса, видео и логи всех сервисов стека.
7. Бюджет: четыре сценария в одном браузере (Chromium), ориентир — до 40 секунд на сценарий и не больше 3 минут на весь набор сверх времени подъёма стека.

### Что специально НЕ проверяется через интерфейс

| Что | Где проверено вместо этого | Почему не в браузере |
|---|---|---|
| Переходы статусов брони, слот в прошлом, некорректные границы слота | unit + mutation | Все комбинации перебираются за миллисекунды; в браузере это десятки минут |
| Двойная бронь при одновременных запросах | component, тест на гонку | Гонку ловит только одновременность на настоящей базе; кликами её не воспроизвести |
| Коды и тела ответов API: `400`, `404`, `409`, `422`, `503` | component + фаззинг | Интерфейс показывает один-два из них; остальные проверяются там, где они рождаются |
| **«Чужую бронь отменить нельзя»** | тест на уровне API | Ключевой пункт. Через интерфейс такой тест доказывает только, что кнопка скрыта. Дыра в авторизации живёт в API и эксплуатируется прямым запросом — значит, и тест должен быть прямым запросом от второго клиента |
| Истечение неоплаченной брони через 15 минут (`DEFAULT_PENDING_TTL`) | component с управляемыми часами | В браузере это либо 15 минут ожидания, либо `sleep`, запрещённый правилом 4 |
| Повтор вебхука, дубликат платежа, идемпотентность | component, тесты повторов и гонок | Вебхук приходит от провайдера, а не из браузера: в интерфейсе этого события просто нет |
| Доставка уведомления, дубликаты событий, очередь ошибок, зависшие сообщения | component `notifier` + smoke | Уведомление уходит во внешний шлюз; на сайте пользователь его не видит |
| Совместимость `booking` и `payments`, version skew | contract (Pact против `main`) | Проверяется без совместного запуска и до сборки образов |
| Что запущена именно свежесобранная версия | smoke, `build_sha` в `/health` (ADR-0003) | Одна строка сравнения вместо сценария |
| Контраст, заголовки, метки полей, роли элементов | gate доступности (axe) на ключевых страницах | Это проверка страницы, а не сценария: дешевле один обход всех страниц, чем проверки внутри каждого e2e |
| Вёрстка и сдвиги разметки | визуальная регрессия, снимки в контейнере с порогом отличий | Там же, отдельным gate |
| Валидация каждого поля формы | проверки на стороне сервера (component), один пример в E2E-3 | Перебор полей в браузере — самый дорогой способ проверить то же самое |

## Последствия

- Плюс: полный набор e2e укладывается в минуты, а не в десятки минут, и добавляется к задаче `stack-smoke` без пересмотра бюджета из ADR-0004.
- Плюс: у каждого сценария записана причина существования. Когда в итерации 5 один из них замигает, разговор начнётся с вопроса «какой риск он закрывает», а не «как бы его починить».
- Плюс: список из четырёх строк — готовый ответ на вопрос «как вы решаете, что автоматизировать через интерфейс».
- Цена: часть поведения интерфейса остаётся непроверенной сознательно: пустые списки, узкий экран, тексты ошибок кроме одного. Это записано здесь, а не забыто.
- Цена: E2E-1 требует, чтобы заглушка PayStub отдавала настоящую страницу оплаты с переходом назад. Сейчас она отвечает одним и тем же `ch_stack` на любой запрос — долг записан в roadmap ещё с итерации 2. Без шаблонов ответов сценарий не собрать.
- Цена: E2E-4 требует фиксированного часового пояса браузера в конфигурации. Запуск без него делает тест бессмысленным, причём зелёным, — самый неприятный вид бесполезного теста.
- Риск: правило «только то, чего нет ниже» держится на дисциплине. Признак нарушения — пятый сценарий, у которого в графе «почему не уровнем ниже» написано «так нагляднее».
- Когда пересматривать: появился экран, где ошибка видна только человеку (дашборд итерации 5); появился второй клиент (итерация 8); или новый сценарий закрывает риск, которого действительно нет ниже — тогда список становится пятью строками осознанно.

## Альтернативы

- **Считать smoke за e2e и не заводить браузер вовсе.** Дёшево и почти работает: smoke уже проходит весь путь по HTTP. Но тогда интерфейс не проверяется ничем, а итерация 4 существует ради него.
- **Проверять интерфейс компонентными тестами фронтенда вместо e2e.** Разумный уровень, но при выборе Jinja + HTMX (ADR-0012) его попросту нет: шаблон рендерится на сервере, отдельного компонента для теста не существует. Если владелец выберет React, этот вариант надо пересмотреть: часть E2E-2 и E2E-3 уедет туда и станет дешевле.
- **Генерировать сценарии записью действий (codegen, record and replay).** Быстро создаёт много тестов и ровно поэтому вреден: получается набор без ответа на вопрос «зачем этот тест», который потом никто не решается удалить.
- **Гонять e2e во всех трёх браузерах.** Утраивает время ради риска, которого у нас нет: аудитория учебного проекта — один человек с Chromium. Появится настоящая аудитория — появится и основание.
