# ADR-0003. Задача CI как эфемерное окружение; постоянный сервер выбираем позже

Статус: принято · 2026-09-19

## Контекст

Бюджет на инфраструктуру нулевой. Бесплатные хостинги дают один сервис на 512 МБ, а условия меняются без предупреждения (Oracle в июне 2026 года молча урезал бесплатный лимит вдвое). При этом тестам нужен весь стек: сервисы, база, очередь, заглушки внешних систем.

## Решение

1. Весь стек описан в одном `compose.yaml`. Задача CI поднимает его (`make up`), ждёт готовности по healthcheck, гоняет тесты и уничтожает (`make down`). Окружение живёт ровно один прогон.
2. Сервис сообщает в `/health`, из какого коммита он собран (`build_sha`). Smoke-тест проверяет, что запущена именно только что собранная версия.
3. Постоянный сервер (демо-стенд, окружения на PR по ссылке, Quality Hub) выбираем отдельным ADR к итерации 4.

## Последствия

- Плюс: ноль затрат и ноль общих стендов. Нет общего состояния — нет целого класса flaky-тестов.
- Плюс: место деплоя — это одна задача в пайплайне. Переезд между хостингами не затрагивает систему.
- Цена: окружение нельзя открыть в браузере и показать другому человеку. Это закроет ADR из пункта 3.
- Цена: время прогона растёт с каждым сервисом. За этим следит бюджет из ADR-0004.

## Альтернативы

- Сразу свой сервер: риск завязать систему на конкретную машину раньше, чем понятны требования.
- Kubernetes: на бесплатных ресурсах не помещается, а для 5 сервисов не даёт ничего, чего не даёт Compose.
