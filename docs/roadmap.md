# План проекта Slot

Slot — тренажёр архитектора автоматизации тестирования. Продукт (запись на услуги) намеренно тонкий; основная работа идёт в инфраструктуре качества вокруг него. План — единственный источник правды о том, что делаем дальше. Любой исполнитель (человек или AI-агент любой модели) начинает сессию с этого файла.

## Как устроена работа

### Роли

- **Владелец** принимает архитектурные решения и объясняет каждый diff своими словами. Он учится на решениях, а не на чтении.
- **AI-агент** готовит варианты с компромиссами, пишет код и тесты, доказывает, что проверки работают, и объясняет сделанное.

### Протокол итерации

Каждая итерация проходит одни и те же шаги. Пропускать шаги нельзя.

1. **Варианты.** Агент приносит 2–3 варианта по каждому архитектурному вопросу итерации: суть, плюсы, цена, когда выбирают в индустрии. Коротко, без отсылок к книгам.
2. **Решение.** Владелец выбирает. Агент записывает ADR со статусом «принято».
3. **Реализация малыми шагами.** Один шаг — один осмысленный diff с тестами. После каждого шага `make check`; если затронуты Dockerfile, Compose или API — полный цикл `make up && make smoke && make down`.
4. **Доказательство от обратного.** Для каждого нового gate или ключевого теста агент показывает, что он падает, когда должен: ломает защищаемое свойство и предъявляет красный результат. Проверка, которая ни разу не упала, не считается сделанной.
5. **Объяснение.** Агент задаёт владельцу 2–3 вопроса по diff. Если владелец не может ответить, агент разбирает по схеме: короткий ответ → реальная авария → вывод для архитектора.
6. **Коммит и пуш** — после объяснения. CI на GitHub должен быть зелёным и укладываться в бюджет времени.
7. **Закрытие.** Обновить в этом файле статус итерации, в `glossary.md` — новые термины, в `test-strategy.md` — новые уровни и gates, в `architecture.md` — схему.

### Сквозные правила

- Продукт тонкий, инфраструктура качества глубокая. Фичи продукта добавляются только тогда, когда без них нечего тестировать.
- Бюджет на инфраструктуру — ноль до итерации 4 (ADR-0003). Платные сервисы — только через ADR с расчётом.
- Gates не ослабляются без ADR (см. `CLAUDE.md`).
- Итерации идут по порядку: каждая опирается на предыдущие. Исключение — итерации 6 и 7 можно поменять местами.
- Если по ходу всплыла находка вне плана (как расхождение версий Python в итерации 0), она чинится сразу, если мала, или записывается в раздел «Долги и находки» в конце файла.

### Оценка объёма

Одна итерация — от 2 до 5 рабочих сессий. При темпе владельца (до 5 часов в неделю) весь план — примерно 6–9 месяцев. Это оценка, а не обязательство: скорость определяет шаг 5, а не написание кода.

## Итерация 1. Ядро бронирования и гонки ✅

**Сделано:** API слотов и броней с жизненным циклом статусов; время передаётся параметром (`FixedClock` в тестах); ADR-0005 — двойную бронь запрещает частичный уникальный индекс, смена статуса — условным обновлением; ADR-0006 — SQLAlchemy 2 + Alembic, миграции в одноразовом контейнере, component-тесты на Testcontainers; тест на гонку; тесты миграций; smoke с настоящей бронью; mutation gate 100% для доменных правил.

**Доказано от обратного:** без защиты 10 из 10 раундов гонки сломаны (до 18 броней на слот); без индекса в миграции падают 4 независимых теста; без одного граничного теста unit-тесты и покрытие зелёные, а mutation gate красный (6/7).

**Время CI:** checks 23 с, component 23 с, stack-smoke 33 с.


**Цель:** у сервиса появляется настоящая доменная логика и база, а у нас — уровень component-тестов и первый тест на гонку.

**Минимум продукта:**
- Мастер публикует слоты: `POST /slots`, `GET /slots?master_id=&date=`.
- Клиент бронирует слот: `POST /bookings`, смотрит `GET /bookings/{id}`, отменяет `DELETE /bookings/{id}`.
- Состояния брони: `pending` → `confirmed` → `cancelled`; `pending` → `expired`. Оплаты ещё нет: подтверждение — отдельный внутренний вызов, который в итерации 2 займёт сервис платежей.
- Без пользователей и авторизации: `client_id` и `master_id` приходят в запросе. Авторизация появится в итерации 4.

**Решения владельца:**
- **ADR-0005. Как не дать двоим занять один слот.** Варианты: уникальное ограничение в базе; блокировка строки (`SELECT … FOR UPDATE`); оптимистичная проверка версии.
- **ADR-0006. Доступ к базе и миграции.** Варианты: SQLAlchemy 2 + Alembic; чистый SQL через psycopg + миграции SQL-файлами.

**Тесты и gates:**
- unit: правила домена (переходы состояний, нельзя бронировать прошедший слот) без базы.
- component: сервис + настоящий Postgres через Testcontainers. Новая цель `make test-component` и отдельная задача CI.
- **Тест на гонку:** N одновременных запросов на один слот → ровно один `201`, остальные `409`. Запускается многократно в одном прогоне, чтобы поймать редкое срабатывание.
- Миграции: применяются на пустую базу; откатываются; схема после миграций совпадает с моделями.
- Отмена и повторное бронирование освобождённого слота.
- **Mutation testing** на доменном модуле: снять базовую линию, затем порог-храповик. Это проверка качества самих тестов, в том числе написанных AI.

**Доказательство от обратного:** убрать выбранную защиту из ADR-0005 → тест на гонку обязан стать красным. Оставить выживших мутантов → gate по mutation score обязан упасть.

**Готово, когда:** гонка воспроизводится и закрыта; component-задача в CI укладывается в бюджет; `test-strategy.md` описывает, что проверяется на unit, а что на component, и почему.

**Термины:** race condition, инвариант, транзакция и уровень изоляции, Testcontainers, component-тест, миграция, mutation score.

## Итерация 2. Платежи: внешний провайдер и контракты ✅

**Сделано (2a):** сервис `payments` со своей базой; идемпотентность через естественные ключи (ADR-0008); подписанные вебхуки; истечение неоплаченной брони без планировщика; WireMock вместо соседей с настоящими сетевыми отказами; smoke на уровне системы со сквозной оплатой.

**Сделано (2b):** контракты по ADR-0007 — Pact в обе стороны с проверкой против `main`, снимки схем и oasdiff, фаззинг Schemathesis, сверка заглушек PayStub с его схемой; единый формат ошибок; выборочный запуск component-тестов в CI.

**Доказано от обратного:** запись события при недоступном `booking` — 2 красных теста; без уникальности платежа — 6; переименование поля в одном PR с потребителем — зелёное против ветки, красное против `main`; фаззинг нашёл 5 дефектов, каждый закреплён обычным тестом.


**Цель:** второй сервис и первая межсервисная граница. Учимся проверять совместимость сервисов без их совместного запуска и тестировать чужой API, которого у нас нет.

**Минимум продукта:**
- Сервис `payments`: `booking` просит создать платёж; `payments` обращается к внешнему провайдеру; провайдер присылает вебхук; `payments` сообщает `booking`, и бронь становится `confirmed`.
- Внешний провайдер — выдуманный «PayStub». Мы пишем его OpenAPI-описание так, как будто получили его от чужой компании, и больше ничего о нём не знаем.
- Неоплаченная бронь истекает (`expired`) и освобождает слот.

**Решения владельца:**
- **ADR-0007. Как проверяем контракт между `booking` и `payments`.** Варианты: контракты от потребителя (Pact); проверка по схеме OpenAPI (Schemathesis + детектор ломающих изменений); оба, с разделением ролей.
- **ADR-0008. Идемпотентность.** Как переживаем повторный вебхук и повторный запрос на создание платежа: ключи идемпотентности, таблица обработанных событий.

**Тесты и gates:**
- contract: ожидания `booking` проверяются в CI сервиса `payments`. Ломающее изменение API блокирует PR.
- component для `payments`: провайдер заменён WireMock. Сценарии отказов: таймаут, `500`, медленный ответ, вебхук дважды, вебхук раньше ответа на создание, вебхук с неверной подписью.
- Фаззинг наших API по OpenAPI: неожиданные входные данные не дают `500`.
- Gate на ломающие изменения OpenAPI между веткой и `main`.
- **Выборочный запуск:** CI запускает задачи только затронутых сервисов (фильтр по путям) плюс контракты соседей.

**Доказательство от обратного:** переименовать поле в ответе `payments` → контрактный тест красный в PR, хотя unit и component самого `payments` зелёные. Отправить вебхук дважды с выключенной идемпотентностью → тест красный.

**Готово, когда:** сквозной сценарий «бронь → оплата → подтверждение» проходит на эфемерном стеке с заглушкой провайдера; в `test-strategy.md` есть таблица «какой риск каким уровнем закрыт» для межсервисной границы.

**Термины:** контракт, потребитель и поставщик, CDC, Pact, OpenAPI, version skew, идемпотентность, вебхук, WireMock, stub/mock/fake, фаззинг, выборочный запуск (TIA).

## Итерация 3. События: очередь и уведомления ✅

**Сделано:** очередь Redis Streams (ADR-0009); транзакционный outbox в `booking` и отдельный процесс-relay; сервис `notifier` со своей базой, группой потребителей, дедупликацией по `event_id` и очередью ошибок; внешний шлюз NotifyGate как заглушка со своей схемой; контракт события — снимок JSON Schema, свой детектор ломающих изменений и контракт со стороны потребителя; outbox в `payments` вместо транзакции во время HTTP-вызова и возврат денег за неподтверждённую бронь (ADR-0010); smoke ждёт результата опросом.

**Доказано от обратного:** выключенный outbox — 8 красных тестов; выключенная дедупликация — ровно один красный тест на дубликат; выключенный счётчик доставок — ровно один красный тест на ядовитое сообщение; переименование поля события — красные `events-check`, `events-breaking` («property 'client_id' was removed») и контрактный тест потребителя.

**Цифры:** `booking` — 93 теста, `payments` — 76, `notifier` — 42, smoke — 7; покрытие 96–97%; mutation score 100% (27/27, 19/19, 35/35).

**Время CI:** changes 10 с, checks 94 с, component 46–49 с на сервис, stack-smoke 64 с. Бюджеты (2/5/8/10 минут) не тронуты, хотя в стеке стало 12 контейнеров вместо 7.

**Что оказалось важнее, чем ожидалось:** «ровно один раз» не существует. Тест на падение после отправки честно показывает два запроса к шлюзу с одним ключом идемпотентности — и это правильный результат, а не недоработка.

**Цель:** асинхронное взаимодействие. Учимся тестировать то, что происходит «когда-нибудь потом», без `sleep`.

**Минимум продукта:**
- `booking` публикует события `booking.confirmed`, `booking.cancelled`, `booking.expired`.
- Сервис `notifier` читает события и отправляет уведомление через внешний шлюз (заглушка).

**Решения владельца:**
- **ADR-0009. Какая очередь.** Варианты: Redis Streams; NATS JetStream; RabbitMQ. Критерии: память на маленьком сервере, гарантии доставки, удобство в тестах.
- **ADR-0010. Гарантии доставки.** Как не потерять событие, если сервис упал между записью в базу и публикацией (паттерн outbox), и как пережить повторную доставку (идемпотентный потребитель, очередь ошибок).

**Тесты и gates:**
- Контракт события: схема сообщения версионируется, ломающее изменение блокирует PR.
- component с настоящим брокером в Testcontainers: повторная доставка; дубликат; нарушенный порядок; «ядовитое» сообщение уходит в очередь ошибок и не блокирует остальные.
- Отказ посередине: `notifier` убит во время обработки → после перезапуска уведомление отправлено ровно один раз.
- Отказ публикации: брокер недоступен в момент подтверждения брони → событие не потеряно.
- Ожидание условия с таймаутом вместо `sleep` — общий помощник для тестов, с понятным сообщением при истечении времени.

**Доказательство от обратного:** выключить outbox → тест «брокер недоступен» красный. Выключить дедупликацию в `notifier` → тест на дубликат красный.

**Готово, когда:** стек из трёх сервисов, базы и брокера поднимается в CI в пределах бюджета; если бюджет превышен — ADR с решением (ускорить или обоснованно поднять).

**Термины:** событие и команда, брокер, at-least-once, outbox, идемпотентный потребитель, очередь ошибок (DLQ), eventual consistency, polling-ассерт.

## Итерация 4. Web, e2e и постоянный стенд

**Цель:** интерфейс, дисциплина минимального e2e и первый настоящий деплой.

**Минимум продукта:**
- Web-клиент: список слотов мастера, бронирование, оплата (через заглушку), отмена.
- Простейшая авторизация клиента и мастера. Сервисы проверяют, что клиент отменяет только свою бронь.

**Решения владельца:**
- **ADR-0012. Стек web и язык e2e-тестов.** Варианты: серверные шаблоны + HTMX; React/TypeScript. Playwright на Python или на TypeScript.
- **ADR-0013. Постоянный сервер и способ деплоя.** Варианты: свой сервер владельца; Oracle Always Free; бесплатный PaaS для части системы. Способ: образы в реестре GitHub, Compose по SSH. Нужны данные о памяти сервера владельца.
- **ADR-0014. Сколько e2e и какие.** Список критических сценариев (3–5) с обоснованием, почему остальное проверяется ниже.

**Тесты и gates:**
- e2e на Playwright: только сценарии из ADR-0014. Подготовка данных — через API, а не через интерфейс. При падении сохраняются трасса, видео и логи сервисов.
- Доступность: автоматическая проверка axe на ключевых страницах как gate.
- Визуальная регрессия: снимки в контейнере (одинаковые шрифты и рендер), порог отличий.
- Авторизация: тесты «чужую бронь отменить нельзя» на уровне API, а не интерфейса.
- **Деплой:** `main` → сборка образов → стенд → smoke против стенда с проверкой `build_sha` → при красном smoke автоматический откат на предыдущие образы.
- **Окружение на PR** с адресом и сроком жизни, если позволит сервер; иначе e2e остаётся внутри задачи CI.
- Секреты: окружения GitHub, отдельный ключ деплоя с минимальными правами, ничего в репозитории.

**Доказательство от обратного:** выкатить сборку с намеренно сломанным `/health` → деплой откатывается сам. Сломать контраст на странице → gate доступности красный.

**Готово, когда:** сайт открывается по адресу; в README есть ссылка на стенд; путь от мержа до проверенного деплоя измерен и записан как метрика.

**Термины:** e2e, Page Object и фикстуры, трасса Playwright, доступность (a11y), визуальная регрессия, реестр образов, откат, окружение на PR, принцип минимальных прав.

## Итерация 5. Quality Hub: flaky и метрики

**Цель:** платформа качества как внутренний продукт. Главная итерация для роли архитектора.

**Минимум платформы:**
- Сервис `quality-hub` принимает результаты прогонов (JUnit XML + метаданные: коммит, ветка, задача, попытка, длительность) от шага в CI.
- Считает: нестабильность теста (упал и прошёл на одном коммите; доля переключений за окно), время обратной связи по задачам, самые медленные тесты, тренды.
- Причина падения: продукт / тест / инфраструктура — сначала вручную, с накоплением данных для итерации 7.
- **Карантин:** список нестабильных тестов отдаётся плагину pytest; тест в карантине запускается, но не блокирует. У записи есть владелец и срок; по истечении срока сборка краснеет. Возврат из карантина — автоматически после N стабильных прогонов.
- На нестабильный тест автоматически заводится задача в GitHub.
- Метрики DORA из API GitHub: частота деплоев, время от коммита до стенда, доля неудачных деплоев, время восстановления.

**Источник данных:** в продукт добавляются **флаги сбоев** (задержка, ошибка, недетерминизм по переключателю) и отдельный набор намеренно нестабильных учебных тестов. Иначе Hub нечего будет показывать.

**Решения владельца:**
- **ADR-0015. Алгоритм определения flaky и политика карантина.** Окно, пороги, срок, кто владелец. Цель уровня сервиса для самого CI: доля нестабильных прогонов не выше X%.
- **ADR-0016. Дашборд: свой или Grafana.** Критерии: память сервера, скорость изменений, ценность для портфолио.

**Тесты и gates:** Hub — полноценный сервис со всеми уровнями из итераций 1–3. Контракт на API приёма результатов: CI — потребитель. Отказ Hub не должен ронять пайплайн продукта.

**Доказательство от обратного:** включить флаг сбоя → Hub находит нестабильный тест за N прогонов, ставит в карантин, заводит задачу; починка → тест возвращается сам. Просрочить карантин → сборка красная.

**Готово, когда:** дашборд открыт по адресу и показывает реальные данные за несколько недель; в `test-strategy.md` описан процесс работы с нестабильными тестами.

**Термины:** flaky, flakiness rate, карантин, цель уровня сервиса (SLO) для CI, DORA, escaped defects, флаг сбоя, chaos engineering, платформа как продукт.

## Итерация 6. Нефункциональные gates и наблюдаемость

**Цель:** производительность, безопасность и диагностика становятся автоматическими проверками с порогами, а не разовыми активностями.

**Решения владельца:**
- **ADR-0017. Цели по производительности.** p95 и доля ошибок для ключевых операций; что проверяем в PR, а что ночью.
- **ADR-0018. Политика по уязвимостям.** ✅ принят досрочно: `docs/adr/0018-vulnerability-policy.md`. Пороги по уровням серьёзности, срок на исправление от даты публикации advisory, список принятых рисков со сроком и владельцем.

**Тесты и gates:**
- Производительность: короткий прогон k6 в PR с порогами; ночной профиль нагрузки; сценарий гонки из итерации 1 под нагрузкой.
- Безопасность: зависимости (SCA) ✅ сделано досрочно (`make audit`, `tools/dependency_audit.py`, `tools/accepted_risks.py`, `security/accepted-risks.toml`); поиск секретов ✅ сделано досрочно (`make secrets`, gitleaks, `security/gitleaks.toml`, `tools/test_secret_allowlist.py`); обе проверки в задаче CI `security` с бюджетом 5 минут. Остаются: сканирование образов, динамическое сканирование (ZAP) эфемерного стека, автоматические обновления зависимостей, SBOM.
- Наблюдаемость: трассировка OpenTelemetry через все сервисы; тест передаёт идентификатор трассы, и отчёт о падении содержит ссылку на неё; структурные логи; один тест с проверкой по трассе.
- **Fitness functions:** сервисы не импортируют друг друга (✅ сделано досрочно: `tools/import_boundaries.py`, цель `make fitness`); слои внутри сервиса; бюджет размера образа; бюджет времени старта.
- Результаты всех новых проверок уходят в Quality Hub.

**Доказательство от обратного:** флаг сбоя «медленный запрос» → gate производительности красный. Добавить зависимость с известной уязвимостью → gate красный ✅ показано на временном проекте с `jinja2==2.10`. Строка, похожая на настоящий секрет → `make secrets` красный ✅ показано. Запись в списке принятых рисков с прошедшей датой → `make audit` красный ✅ показано. Импортировать код соседнего сервиса → fitness function красная.

**Готово, когда:** по упавшему e2e можно за минуту дойти до трассы и лога нужного сервиса; все пороги записаны в ADR.

**Термины:** p95/p99, SLO, профиль нагрузки, SAST/DAST/SCA, SBOM, список принятых рисков, трасса и спан, OpenTelemetry, fitness function.

## Итерация 7. AI-ассистент и evals

**Цель:** научиться тестировать недетерминированную LLM-функцию так же строго, как обычный код.

**Минимум продукта:** сервис `assistant`: фраза «запиши меня к Анне завтра после шести» → структурированный запрос (мастер, интервал дат, ограничения по времени) → поиск слотов через API `booking` → предложение. Бронирует только после подтверждения клиента.

**Решения владельца:**
- **ADR-0019. Модель, провайдер и бюджет.** Лимит расходов в месяц; в PR — записанные ответы модели, настоящие вызовы — ночью или вручную.
- **ADR-0020. Методика evals и пороги.** Что проверяет код, что — модель-судья, какой порог блокирует изменение промпта.

**Тесты и gates:**
- Эталонный набор на 50–100 примеров: относительные даты, неоднозначность, неполные запросы, другой язык, запросы не по теме. Пополняется из найденных ошибок.
- Проверки кодом по структурированному ответу — основа. Модель-судья — только для качества уточняющих вопросов, с калибровкой на примерах, размеченных владельцем.
- Устойчивость: каждый пример k раз, метрика pass^k.
- Регрессия: изменение промпта или модели проходит evals с порогами; результаты, стоимость и задержка уходят в Quality Hub.
- Безопасность: набор prompt-инъекций; ассистент не может действовать от имени другого клиента — это обеспечивает авторизация API, а не промпт, и тест это доказывает.
- Разбор причин падений тестов в Quality Hub с помощью модели — как вторая AI-функция, со своими evals на накопленных размеченных данных.

**Доказательство от обратного:** ухудшить промпт → gate evals красный. Инъекция «отмени бронь клиента 42» → действие не выполнено.

**Готово, когда:** есть отчёт evals в Hub с динамикой; расходы в пределах бюджета; политика использования AI-агентов в разработке (`CLAUDE.md`) дополнена опытом проекта.

**Термины:** evals, эталонный набор, модель-судья и её калибровка, pass@k и pass^k, prompt-инъекция, избыточные полномочия агента, записанные ответы.

## Итерация 8. Мобильный клиент

**Цель:** третий канал доставки и понимание цены мобильного тестирования.

**Решения владельца:**
- **ADR-0021. Технология клиента.** Варианты: PWA; Flutter; React Native. Критерий — стоимость разработки и тестирования для одного человека.
- **ADR-0022. Ферма устройств.** Эмулятор в CI, облачная ферма или свои устройства — расчёт стоимости на бумаге для команды из 20 человек, даже если выбираем эмулятор.

**Тесты и gates:** сценарии Maestro на эмуляторе Android в GitHub Actions; клиент — ещё один потребитель контрактов `booking`; бюджет времени задачи; статистика нестабильности мобильных тестов в Hub отдельно от остальных.

**Доказательство от обратного:** ломающее изменение API → красный контракт мобильного клиента ещё до запуска эмулятора.

**Готово, когда:** сценарий бронирования проходит на эмуляторе в CI в пределах бюджета.

**Термины:** эмулятор и реальное устройство, ферма устройств, Maestro, Appium, стоимость владения.

## Долги и находки

Сюда записывается всё, что всплыло вне плана и не было исправлено сразу.

- Команда `gh run watch --exit-status` вернула код ошибки на успешном прогоне (2026-09-19). Статус прогона проверять через `gh run view --json conclusion`.
- `/health` отвечает «жив», даже если база недоступна. Нужен отдельный `/ready`, который проверяет базу, и разница между ними в healthcheck. Кандидат в итерацию 4 (деплой) или 6 (наблюдаемость).
- ~~Платёж с `needs_refund = true` никто не обрабатывает~~ — закрыто в итерации 3 (ADR-0010, п. 8).
- ~~Обработка вебхука держит транзакцию открытой во время HTTP-вызова~~ — закрыто в итерации 3 (ADR-0010, п. 7).
- ~~Клиент WireMock скопирован в тесты каждого сервиса~~ — решено в ADR-0011: копии остаются, условия пересмотра записаны.
- ~~У фоновых процессов нет healthcheck~~ — закрыто: каждый цикл пишет время в файл, healthcheck проверяет его возраст. Нашлось в CI: `docker compose up --wait` считает контейнер без healthcheck ошибкой. Проверено от обратного: замороженный `SIGSTOP` процесс краснеет за 56 секунд. Признак живости не отвечает на вопрос «а работает ли полезно» — длина неопубликованного outbox нужна отдельно (итерация 5).
- В outbox нет предела попыток: сообщение, которое не удаётся доставить, останавливает очередь сообщений за собой. Это осознанный выбор (порядок важнее пропускной способности), но нужен сигнал — длина неопубликованного outbox и возраст самой старой записи как метрики. Кандидат в итерацию 5.
- Очередь ошибок `slot.bookings.v1.dead` никем не читается: сообщение туда попадает молча. Нужны длина очереди как метрика и разбор содержимого. Кандидат в итерацию 5.
- `notifier` не удаляет и не архивирует старые записи `notifications`, `booking` — опубликованные строки outbox. На сроке жизни проекта это неважно, но правило хранения нужно записать до постоянного стенда. Кандидат в итерацию 4.
- Время «простоя» сообщения (`idle_ms`, 30 секунд по умолчанию) нигде не обосновано расчётом. В тестах оно равно нулю. Для стенда нужно связать его с таймаутом шлюза.
- Заглушка PayStub в стеке отвечает одним и тем же `ch_stack` на любой запрос. Для e2e в итерации 4 понадобятся шаблоны ответов.
- Фаззинг в PR детерминирован и ограничен 40 примерами на операцию. Нужен ночной прогон со случайным зерном и большим числом примеров; находки — в регрессионные тесты. Кандидат в итерацию 5 (Quality Hub).
- pact-python не закрывает сокет своего сервера состояний (`pact/_server.py`: `shutdown()` без `server_close()`). Предупреждение заглушено точечно. Стоит сообщить авторам.
- Заголовок `Allow` для `405` собираем сами: FastAPI указывает методы только первого подходящего маршрута. При обновлении FastAPI проверить, не исправлено ли.
- Ветка с авторизацией в `booking` (коммит «Booking learns who is calling») не пройдёт новый поиск секретов: правило `slot-secret-literal` находит значения в `contracts/auth/token.v1.json`, `services/booking/tests/component/conftest.py` и `services/booking/tests/unit/test_auth.py`, а правило `generic-api-key` — токены-примеры в том же контракте. Значения намеренные и тестовые, но при слиянии в `main` каждое придётся внести в `security/gitleaks.toml` с объяснением и в `tools/test_secret_allowlist.py` (ADR-0018). Найдено сканированием истории 2026-09-20.
- Анализ влияния знает сервисы списком в `tools/changed_services.py`. Новый сервис нужно добавить туда, иначе его файлы запустят всё (безопасно, но медленно).
